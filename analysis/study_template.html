What actually happens when Redis looks up a key

Six experiments on a Redis server built from source on a 2015 laptop: how lookup time scales, what it costs when the hash table grows, where compact encodings stop paying off, how one slow command stalls every client, and how long expired keys keep using memory.

Lookup cost

GET is O(1), and the round trip costs ~{{RT_X}}× more than the lookup

A GET took {{GET_MIN}}–{{GET_MAX}} µs inside Redis whether the database held 1,000 keys or {{MAXKEYS}}. The Python client saw a ~{{CLIENT_P50}} µs round trip for the same call.

Rehashing

When the table doubles, writes slow down for a long stretch, not for one big pause

Each time the key count passes a power of two, Redis allocates a table twice the size and moves buckets over a few at a time on later commands. While that runs, a batch of 1,000 SETs costs {{MED_IN}} µs instead of {{MED_OUT}} µs.

Encodings

Small collections trade lookup speed for memory, up to a configured limit

A small hash is stored as a listpack, a packed array that is scanned from the start. At {{H_LAST}} fields HGET took {{H_US_B}} µs. At {{H_AT}} Redis converts it to a real hash table: HGET drops to {{H_US_A}} µs and total memory grows {{H_MEMX}}×.

Single thread

One slow command makes every client wait

A separate process sent GETs nonstop (normally {{BASE_US}} µs each) while another client ran expensive commands. During KEYS * its GETs waited up to {{KEYS_MS}} ms; DEL on a 1M-field hash held everyone for {{DEL_MS}} ms. SCAN and UNLINK did the same jobs with stalls of {{SCAN_MS}} ms and {{UNLINK_MS}} ms.

{{BL_ROWS}}

Longest wait seen by the probing client while each command ran, on a database of 1M keys. SCAN does more total work ({{SCAN_SERVER}} ms of server time) but in small steps. UNLINK passes the freeing work to a background thread.

Pipelining

Batching commands gave {{PP_X}}× the throughput

One GET per round trip reached {{PP_1}} ops/s. Sending 1,000 per round trip reached {{PP_MAX}} ops/s; beyond a few hundred, the Python client becomes the limit, not Redis.

Expiry

Expired keys keep their memory until the background cycle finds them

1M keys all expired at the same instant and nobody read them. Half were gone {{T50}} s later, all of them after {{T100}} s, and until then they held their share of {{EX_MEM}} MB.

Method notes

  • Server-side numbers come from INFO commandstats, so they leave out the network and the Python client. Client numbers are shown only where the round trip is the point.
  • The blocking probe runs in its own process. A first version used a thread, and Python's GIL stalled it whenever the main thread parsed a large reply. That made KEYS * look like 600 ms of blocking when the server spent 58 ms.
  • Each experiment starts from FLUSHALL. Persistence is off so snapshots and AOF writes don't add noise.
  • Single run on a laptop with frequency scaling on. Treat the absolute numbers as this machine's; the shapes and ratios are the findings.
