What actually happens when Redis looks up a key

Six experiments on a Redis server built from source on a 2015 laptop: how lookup time scales, what it costs when the hash table grows, where compact encodings stop paying off, how one slow command stalls every client, and how long expired keys keep using memory.

Lookup cost

GET is O(1), and the round trip costs ~84× more than the lookup

A GET took 0.85–1.33 µs inside Redis whether the database held 1,000 keys or 5M. The Python client saw a ~98 µs round trip for the same call.

Server time from INFO commandstats (usec_per_call), 10,000 random GETs per size; keys created with DEBUG POPULATE. Memory came to ~73 bytes per key including overhead.

Rehashing

When the table doubles, writes slow down for a long stretch, not for one big pause

Each time the key count passes a power of two, Redis allocates a table twice the size and moves buckets over a few at a time on later commands. While that runs, a batch of 1,000 SETs costs 668 µs instead of 349 µs.

Encodings

Small collections trade lookup speed for memory, up to a configured limit

A small hash is stored as a listpack, a packed array that is scanned from the start. At 512 fields HGET took 4.1 µs. At 513 Redis converts it to a real hash table: HGET drops to 0.7 µs and total memory grows 4.9×.

Single thread

One slow command makes every client wait

A separate process sent GETs nonstop (normally 118 µs each) while another client ran expensive commands. During KEYS * its GETs waited up to 184 ms; DEL on a 1M-field hash held everyone for 113 ms. SCAN and UNLINK did the same jobs with stalls of 1.8 ms and 0.3 ms.

KEYS * (1,000,000 keys)183.9 ms
SCAN full iteration1.8 ms
DEL hash (1,000,000 fields)112.8 ms
UNLINK hash (1,000,000 fields)0.3 ms

Longest wait seen by the probing client while each command ran, on a database of 1M keys. SCAN does more total work (355 ms of server time) but in small steps. UNLINK passes the freeing work to a background thread.

Pipelining

Batching commands gave 10.8× the throughput

One GET per round trip reached 9,624 ops/s. Sending 1,000 per round trip reached 103,793 ops/s; beyond a few hundred, the Python client becomes the limit, not Redis.

Expiry

Expired keys keep their memory until the background cycle finds them

1M keys all expired at the same instant and nobody read them. Half were gone 3.5 s later, all of them after 8.1 s, and until then they held their share of 104 MB.

Keys written with one absolute deadline (PXAT). Removal comes only from the active expire cycle, run hz = 10 times a second under a CPU budget (active-expire-effort = 1).

Method notes

  • Server-side numbers come from INFO commandstats, so they leave out the network and the Python client. Client numbers are shown only where the round trip is the point.
  • The blocking probe runs in its own process. A first version used a thread, and Python's GIL stalled it whenever the main thread parsed a large reply. That made KEYS * look like 600 ms of blocking when the server spent 58 ms.
  • Each experiment starts from FLUSHALL. Persistence is off so snapshots and AOF writes don't add noise.
  • Single run on a laptop with frequency scaling on. Treat the absolute numbers as this machine's; the shapes and ratios are the findings.
